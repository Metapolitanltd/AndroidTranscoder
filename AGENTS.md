## Long-term Knowledge

### Architecture

<!-- lore:019daf18-4217-7639-80a3-71292081e9e5 -->
* **AndroidTranscoder fork: Vero namespace + dual publishing**: This repo is Vero's private fork of \`otaliastudios/transcoder\`. \`lib-legacy\` namespace was rebranded \`com.otaliastudios.transcoder\` → \`com.vero.transcoder.legacy\`, and \`io.deepmedia.transcoder\` → \`com.vero.transcoder\` in \`lib\`. This is a breaking change for downstream consumers even on patch version bumps — R class package, manifest, resources all shift. \`lib/build.gradle.kts\` reads \`rootProject.file("version.properties")\` at configuration time (no existence check — fails hard if missing) and registers BOTH the \`deployer\` plugin and \`maven-publish\` publications, which can produce overlapping/conflicting artifacts if a CI job invokes both. Pick one publishing mechanism per module before releasing.

<!-- lore:019daf29-fc3e-7d2e-856b-a86aee62f4bc -->
* **AndroidTranscoder timestamp pipeline: two-layer monotonic enforcement**: Timestamps pass through TWO monotonic guards: (1) \`Timer.SegmentInterpolator.interpolate()\` per-segment after user \`TimeInterpolator\` runs — feeds both \`ReaderTimer\` (pass-through) and \`DecoderTimer\` (decode/re-encode), so all downstream stages see strictly-increasing per-track timeline. (2) \`MonotonicTimeInterpolator\` per-track inside \`DefaultDataSink.writeTrack()\` line 164, applied right before \`MediaMuxer.writeSampleData\`. The fix for malformed FLV/AVI inputs (non-monotonic H.264 PTS) lives at layer 1 (correct architectural point — both pass-through and re-encode benefit). Layer 2 is a final safety net at mux time. Both layers use \`next.coerceAtLeast(prev + 1)\` and both have the Long.MAX\_VALUE overflow risk \[\[019daf18-4213-785a-8b26-6d417dac0749]].

### Gotcha

<!-- lore:019daf29-fc3e-7d2e-856b-a869319421a4 -->
* **AndroidTranscoder MonotonicTimeInterpolator: same Long overflow at prev+1**: \`lib/.../time/MonotonicTimeInterpolator.kt:25\` — used by \`DefaultDataSink\` as the final per-track guard before \`MediaMuxer.writeSampleData\` — has the same overflow pattern as \`Timer.SegmentInterpolator\` \[\[019daf18-4213-785a-8b26-6d417dac0749]]: \`next.coerceAtLeast(prev + 1)\` overflows to \`Long.MIN\_VALUE\` when \`prev == Long.MAX\_VALUE\`, silently allowing a backward PTS into the muxer. Note: this means the pipeline has TWO monotonic guards (SegmentInterpolator per-segment, then MonotonicTimeInterpolator per-track in DefaultDataSink line 164) — fixing only one is insufficient. Apply the same saturating-increment fix: skip \`+1\` when \`prev == Long.MAX\_VALUE\`. Pre-existing, not introduced by the timestamp-monotonic branch.

<!-- lore:019daf18-4213-785a-8b26-6d417dac0749 -->
* **AndroidTranscoder Timer.kt: monotonic coercion overflows at Long.MAX\_VALUE**: In \`lib/.../internal/Timer.kt\` the monotonic timestamp guard does \`interpolatedLast + 1L\` then \`coerceAtLeast\`. If a custom \`TimeInterpolator\` ever returns \`Long.MAX\_VALUE\`, the \`+1L\` overflows to \`Long.MIN\_VALUE\` and \`coerceAtLeast\` silently allows huge backward PTS jumps into MediaMuxer. Fix: treat both \`Long.MIN\_VALUE\` (uninitialized sentinel) and \`Long.MAX\_VALUE\` as skip-increment cases — use raw interpolated value as \`minNext\` instead of \`interpolatedLast + 1L\`. Related risk: silent +1µs coercion masks bad interpolators that return constant/decreasing values; consider a max-correction threshold that throws rather than collapsing the timeline into microsecond-spaced frames.

<!-- lore:019daf18-4207-7b21-83ce-6e888fd95c4c -->
* **AndroidTranscoder: checkVideoSample must guard codec-config/empty buffers and run only at muxer write**: In \`lib/.../sink/DefaultDataSink.java#writeTrack\`, calling \`mMuxerChecks.checkVideoSample\` on every incoming buffer breaks two ways: (1) MediaCodec emits \`BUFFER\_FLAG\_CODEC\_CONFIG\` / zero-size buffers before the first keyframe — these lack \`BUFFER\_FLAG\_SYNC\_FRAME\` and crash with \`InvalidOutputFormatException\`; (2) when video arrives before muxer start, samples get enqueued but each is re-validated as \`firstSample=true\`, so the second queued P/B-frame crashes. Fix: move the check inside the \`if (mMuxerStarted)\` branch and guard with \`bufferInfo.size > 0 && (flags & BUFFER\_FLAG\_CODEC\_CONFIG) == 0\`. Also only set \`mFirstSampleWritten\` after a real (non-config, non-empty) sample is written to muxer, not on enqueue.
